## Why I Am Revisiting Data Structures

Data Structures was a course that I was very wary about. I was most intimidated
by how broad and complicated the subject could possibly be. I realized the
course was manageable when I put in the time and carefully reviewed the
material. This is a university course, so I might as well take advantage of
that.

The main goal of this blog series will be to revisit the topics in the course
with fresh eyes. Although I was able to complete all the projects in the course,
which mainly involved implementing data structures from scratch, there were a
few topics I was more concerned about just finishing for the grade at the time
rather than developing a deep understanding and intuition for.

I was inspired to revisit the topics of this course when I updated my portfolio
project to include my HashMap project. It reminded me of how fascinating it was
learning the mechanics of a data structure. A previous manager of mine said, “in
software there is no magic.” I hope to internalize that, and allow that to
encourage me to dive deep.

## The Data Structures I Want to Explore

The topics that I am most interested in revisiting are AVL trees, for
complexity, and MinHeaps, for unfamiliarity. Some other topics I am especially
excited to revisit would be binary search trees, stacks, and queues. I hope to
be able to deepen my understanding, and make interesting connections between
data structures.

## How This Relates to LeetCode

It might seem natural to connect this work to DSA interview preparation.
However, I am not yet convinced that understanding how data structures are
implemented directly improves LeetCode-style problem-solving. I think that
understanding the inner workings really only helps with understanding the time
complexity of LeetCode solutions. Solving LeetCode-style problems just seems
like a different skill than learning how these data structures are implemented.
As I progress through this series and solve more LeetCode problems, I plan to
revisit this observation and see whether my perspective changes.

> **Note:** There are some exceptions that I have found, like understanding
> different traversals with binary search trees and using those to directly
> solve some LeetCode problems.

## Thinking Like an Engineer

Where I do think learning the inner workings is important is to start thinking
more like an engineer. When we understand the inner workings we can understand
the tradeoffs. As an engineer, we should aim for the most efficient solution
that is reasonably available. To be able to determine efficiency, we must
understand our tools. There should be a baseline of knowledge for engineers;
Engineers do not need to be data-structure experts, but we should understand our
tools well enough to make informed decisions.

## What to Expect From This Series

I hope to be able to use this as a resource for myself, and for it to possibly
be useful for others. I feel that I may make observations or explain things in
ways that may only make sense to me. If anything is unclear, or if you would
simply like to discuss the subject, please reach out!

To add structure and maximize the value of future posts, I will focus on
answering these questions:

1. What problem does it solve?
2. How does it work internally?
3. What are its time and space tradeoffs?
4. When would you choose it over an alternative?
5. How does this knowledge apply to engineering or interviews?

Thank you for reading and I look forward to progressing with this blog series.
